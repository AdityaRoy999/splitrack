# Firebase and AWS integration

The app authenticates through Firebase Email/Password or Google credentials and reads real data from the existing AWS SplitTrack API. Public Firebase values are in ignored `.env`; use `.env.example` for another checkout. Both mobile platforms read Firebase configuration from ignored local `.env` or GitHub Actions Secrets; all six values must be provided together. Firebase passwords/refresh tokens are not sent to AWS. Native sessions use encrypted SecureStore; web uses Firebase browser persistence.

The existing `splittrack-backend` stack in `ap-south-1` contains the API, tables and private media bucket. Backend source is in the separate, ignored `AWS-SplitTrack` Git repository. Its README and frontend/backend mapping document the API and deployment procedure.

## App behavior

- New users have no sample payment profiles, members, trips or transactions. Nine starting expense categories are configuration.
- Signup, login, password reset, username onboarding, photos and signout use Firebase and the authenticated AWS profile API.
- Member search uses registered profiles by name/username prefix. Display names may repeat; usernames are unique. Emails and account lists remain private.
- Expenses, statement imports, payment profiles, categories, trip membership, partial settlements and preferences save through typed endpoints. Financial totals and analytics come from the server.
- UPI QRs include the receiving UPI ID and debt amount. Users confirm payment in their UPI app; marking it paid is a user-confirmed ledger action, not a bank-verified receipt.
- Removing members preserves their historical debts. A fresh ledger hides old private history by generation, while retaining existing AWS records and the registered profile.
- Both mobile platforms retain per-UID validated profiles, authoritative snapshots and pending submissions across relaunches. A saved Firebase session with completed onboarding can open its cached ledger offline. Accounts remain isolated by UID. Four legacy demo/session keys are discarded. Tab changes use loaded data; startup, foregrounding and periodic refresh synchronize AWS. Expanded ledger pages are revalidated during refresh. Auth and offline behavior are shared between iOS and Android; iOS rendering and design remain intact.
- Both mobile platforms persist expense/income/transfer creations, settlement receipts and imported entries before acknowledging them. Expense/income/transfer balance effects overlay the authoritative snapshot; settlement receipts capture an explicit amount and wait for server validation before changing balances. Exact payloads and idempotency keys survive timeouts, relaunches and reconnection. Server acknowledgements are checkpointed before queue removal. Pending transactions are visible in the ledger and trip details; edits and deletion wait for synchronization. First sign-in, onboarding, profile/membership changes and media uploads still require a connection.
- Content-based duplicate matching is removed in the deployed backend. Separate transactions remain separate even when amount, payer and participants match. Request IDs still make retries idempotent. Mobile submissions use `durableRetry`; older pending payloads retain their exact bytes. Definitively rejected legacy duplicates receive fresh keys. Only an accepted authoritative newer ledger generation retires old drafts. Other failed entries remain reviewable in Settings, without a full-width sync banner.
- Password users can choose **Settings → Sync with Google** and select the Google account with the same email. Firebase links the Google credential to the signed-in user's existing UID; password sign-in, the AWS ledger, groups and offline queue stay with that account. Recent-login requests prompt for the current password. Credentials belonging to another Firebase UID are rejected without merging financial records.
- Repeating email/password signup shows **Account already exists**, with **Continue to sign in** and **Sign up with a different account**. A Google collision with an existing password account retains its credential only in memory, then offers explicit password sign-in and linking. Failed optional linking remains visible in the same sheet after sign-in; users can retry or keep using their password. Cancel, signout and session changes discard pending linking intent.

## Build configuration and verification

The mobile GitHub workflows receive seven public API/Firebase settings through repository secrets and the optional Places key through a secret. AWS/Firebase admin credentials remain outside mobile bundles. Both mobile Google sign-in flows validate the OAuth clients against the Firebase project and handle cancellation and provider errors; Android also checks Play Services. The supplied iOS bundle/client/callback values match the app. The supplied Android Google configuration lacks a signing-certificate registration; register the package and actual APK signer SHA-1 and enable the Google provider before device sign-in can succeed. See [Google sign-in setup](android-google-sign-in.md) and the [verified APK certificate and console steps](android-signing-certificate.md). The Android workflow publishes certificate diagnostics and can compare an optional expected SHA-1. Both workflows run auth regression checks; iOS rendering and native identity configuration stay intact.

Mobile workflows build independently: pushes to `android` run only the APK workflow, and pushes to `ios` run only the IPA workflow. Manual dispatch must select the matching platform branch. Pushes to `main` run neither mobile build. Each verifies the required public configuration before building. iOS publishes the unsigned SideStore IPA and updates its feed only on `ios`; Android publishes a signed testing APK with an increasing version code and verifies its signature. Feed-only commits do not start another mobile build. Use the [iOS SideStore source](https://raw.githubusercontent.com/AdityaRoy999/splitrack/ios/apps.json) for future feed updates. See [platform branches](mobile-builds.md#platform-branches).

Run `npx expo lint`, `npx tsc --noEmit`, and `node --test scripts/*.test.mjs`, then export the Android and iOS JavaScript bundles. Backend checks use `npm run validate` in the separate `backend/` checkout. Device validation should cover airplane-mode save, force-close/reopen, reconnect, a duplicate's Continue/Cancel choices, switching users, and Google sign-up/sign-in with the registered certificate. Device rendering, native persistence and UPI handoff require testing the built IPA/APK; JavaScript exports do not prove native frame rates.
